Customer Portal Toolkit documentation

This guide explains how Jira Service Management administrators install, configure, preview and publish supported customer portal content.

Product scope

Customer Portal Toolkit is a Jira Service Management Cloud app. It provides an administrator builder and renders configured content on supported customer portal surfaces, including request details, the request side panel, the portal header and request actions. Availability depends on the customer's JSM plan, project type, request type, fields, workflow, permissions and Atlassian APIs.

Installation

  1. A Jira administrator installs the current Marketplace version on the intended Jira Cloud site and reviews the requested scopes and data disclosures.
  2. Open Customer Portal Toolkit from global administration or a supported project's settings.
  3. Review the installation-wide AI, product analytics and two-person publication settings. They are disabled by default.
  4. Select a JSM project and inspect detected request types, fields, workflow, SLA and other capabilities.
  5. Apply a starter template or create a layout, preview it with authorized test data, resolve validation errors and publish.
  6. Complete a controlled customer acceptance test before using the configuration broadly.

Configuration scopes

Configuration can be maintained at global, project and request-type scope. Narrower scopes inherit from their parent and may apply bounded overrides. Drafts are editable; a published version is the configuration read by the portal runtime. Publication uses revision checks so one administrator does not silently overwrite another administrator's newer work.

Widget and data behavior

  • Current-request widgets read supported request fields, public activity, participants, organizations, SLA, service and related metadata only when the current actor and JSM API permit it.
  • Aggregate widgets use compiled, project-bound queries and return only privacy-treated counts, buckets, ranges, percentages, durations or short series. They do not return matching requests or cross-request content.
  • Action widgets support a closed set of operations. The backend rechecks the published policy, current user's permissions and current workflow immediately before mutation.
  • Public header widgets can show explicitly public configuration-backed content to anonymous or generic unlicensed visitors. They cannot read a request, run aggregates, execute actions, personalize content or use AI.
  • AI widgets require installation-wide and per-widget opt-in and use Atlassian-hosted Forge LLM. Core portal behavior does not depend on AI.

Preview and publication

The builder can preview supported customer, project-agent and project-administrator audiences, locations, locales and device sizes. Preview is a configuration tool, not proof that every tenant capability is available. Validate the published result in the real JSM customer portal with an authorized test account.

When two-person publication is enabled, a different eligible administrator must approve the exact draft revision within 24 hours.

Security and privacy settings

  • Use the smallest audience and scope that meets the business need.
  • Keep aggregate privacy minimums at or above the enforced minimum of five.
  • Use synthetic or authorized data for previews and support reproductions.
  • Do not place credentials, tokens, secrets or unnecessary sensitive data in widget copy, links or support tickets.
  • Review Privacy, Security, Data Processing and AI Transparency before rollout.

Known limitations

  • Jira Server and Jira Data Center are not supported.
  • The app does not replace the JSM portal or provide arbitrary row-level customization of JSM's native My requests table.
  • Feature availability varies by JSM plan, tenant, project type, account class, workflow and Atlassian API support.
  • Some aggregate metrics are prepared asynchronously and may show a safe unavailable or stale state while refreshing.
  • Forge LLM is an optional Preview platform capability and may be unavailable, limited or changed by Atlassian.
  • Version 1.0 does not provide a file-based configuration export/import or a customer-restorable app backup.
  • Registry presence and documentation do not override a missing tenant capability or permission.

Troubleshooting

  1. Confirm the app version and that installation is current.
  2. Confirm the user, project, request type, location and device match the published visibility policy.
  3. Check Jira/JSM permissions and whether the required field, SLA, Assets or workflow capability exists.
  4. Open the builder preview and resolve any validation or capability warning.
  5. If the problem remains, contact Mederak Apps Service Desk with the site hostname, safe timestamps, location, actor class and reproduction steps. Do not send customer request content or credentials.
